# キャラクター素材

## 保存場所・命名規則

実際にアプリで使う画像は [public/characters/](../../public/characters/) に置く。

ファイル名: `c{キャラID2桁}_{種類}{連番2桁}.png`

- `t01` : 立ち絵（動かさない前提の一枚絵。詳細を綺麗に見せるためのもの）。**現在はキャラクター画面では使用していない**（下記の待機アニメーションに差し替え済み）。将来、詳細確認用の別画面などで使う可能性はあるためファイル自体は残している
- `d01` : 戦闘用ドット絵（3頭身、通常時）
- `d02` : 戦闘用ドット絵（3頭身、攻撃時）
- `d03` : 戦闘用ドット絵（3頭身、ダメージ時）

1キャラにつき上記4枚が基本セット。キャラが増える場合は `c02`, `c03`, ... と番号を増やす。

現在は `c01`〜`c04` の4キャラ分（計16枚）が揃っている。各キャラの名前・設定・ゲーム内での役割は未定（今後決める）。

### キャラクター画面用：ドット絵待機アニメーション

[public/characters/idle/](../../public/characters/idle/) に `c{キャラID2桁}_idle_sheet.png` として1キャラ1枚のスプライトシートを置いている。素材は外部の画像制作リポジトリ（`hirogames_images`、`CHARACTER_SCREEN_ASSETS.md`が引継ぎ入口）で作られたもので、1コマ486×810px・8列×5行・40コマ・100ms間隔（4秒ループ）という仕様で4キャラ共通。表示側の実装詳細は[screens/character-view.md](./screens/character-view.md)を参照。

### 戦闘画面用：攻撃アニメーション

[public/characters/attack/](../../public/characters/attack/) に `c{キャラID2桁}_attack_{連番2桁}.png`（00〜05の6枚、1体につき）として置いている。素材は外部の画像制作リポジトリ（`hirogames_images/docs/CLAUDE_HANDOFF_BATTLE_ATTACK_ANIMATIONS.md`が引継ぎ入口）で作られたもので、それまで静止画1枚（`d02`）だった戦闘中の攻撃ポーズを、6フレームのアニメーションに差し替えたもの（ユーザー確認済み）。

- 各フレームは512×512pxの透過PNG。1動作6フレーム、ループなしで1回再生し、終了後は通常ポーズ（`d01`）に戻る
- フレームごとの表示時間（ms）はキャラごとに異なり、`lib/characters-info.ts`の`CharacterBaseInfo.assets.attackAnimation.durationsMs`に持たせている（[skills.md](./skills.md)の攻撃力バフ等とは無関係、演出のみのタイミング）
- 4キャラとも、インデックス4（0始まり）が実際に攻撃が発生する瞬間のフレーム（振り下ろす／氷を放つ／風を放つ／矢を放つ）で統一されている。戦闘側の実装（[battle-test.md](./screens/battle-test.md)参照）は、この共通性を利用してダメージ反映のタイミングをフレーム4に固定している
- `d02`（旧・静止画の攻撃ポーズ）は現在未使用だが、フォールバック用にファイル・データともに残している
- 敵キャラクターの攻撃は対象外（引き続き静止画のまま）。敵側にも同様のアニメーションを作る場合は、この節と同じ構成で追加できる想定
- 攻撃フレーム（512×512の正方形キャンバス）と通常ポーズ（`idle`/`d01`、971×1619の縦長キャンバス）は、キャラ本体がキャンバスに占める割合も、足元がキャンバス内のどこにあるかも全く異なる。単純に同じ表示幅で重ねると、①足元の位置が通常ポーズよりかなり上にズレる、②見た目の大きさも変わって見える、という2つの問題が起きる（ユーザー指摘・実測で確認済み。「小さく見える」のではなく「立ち位置そのものがズレる」が本質的な原因だった）。両ポーズの画像を`sharp`で解析（非透過ピクセルの外接矩形から足元＝インクの最下点を比較）し、通常ポーズに揃うよう`footShiftPercent`（攻撃画像を下にずらす量、画像自身の高さに対する%）・`bodyScale`（足元を基準に拡大する倍率）・`transformOriginY`（スケールの基準点＝攻撃画像自身の中の足元位置、%）の3値をキャラごとに算出し、`CharacterBaseInfo.assets.attackAnimation`に持たせている。適用は`transform: translateY(footShiftPercent%) scale(bodyScale)` / `transformOrigin: 50% transformOriginY%`（[battle-test.md](./screens/battle-test.md)参照）。フレーム0を基準に算出した値を6フレーム共通で使っている（フレーム間の足元位置のズレは実測で数%程度に収まり、視認上問題ないことを確認済み）

## 画像の作り方

Claude自身は画像生成AIを持たないため、キャラクター素材は外部の画像生成AI（NijiJourneyなど）でユーザー側が生成し、`WebApp_game/サンプル画像/` フォルダに置いてもらう運用にしている。

- `サンプル画像/` フォルダの中身は消したり移動させたりしない（ユーザーの作業用フォルダのため）。新しい画像が追加されたら、`public/characters/` に**コピー**して使う
- `サンプル画像/` は `.gitignore` で除外しており、GitHubには上げない。実際にアプリで使う `public/characters/` 側だけをコミットする

## 画像の加工

- 戦闘用ドット絵（`d01`〜`d03`）は、生成された時点では白背景が焼き込まれているため、`sharp`（Next.jsが依存として持っているライブラリ）を使って白背景を透過に変換してから `public/characters/` に置いている。ゲーム内の背景色（パステルミント）に重ねても白い縁が出ないことを確認済み
  - **透過処理は「画像の外周から連結している明るい画素だけ」を透過するフラッドフィル方式で行うこと。** 単純に「明るさが閾値を超えた画素は全部透過」という判定をすると、キャラクター内部の白いハイライト（髪・肌・衣装の明るい部分）まで巻き込んで穴だらけになる事故が過去に発生した（c02, c03の白系衣装キャラで顔やドレスが透けてしまった）。外周からのフラッドフィルなら、外周とつながっていない内部の明るい画素は透過されずに残る
  - 透過処理後は、透明・半透明画素をマゼンタなど目立つ色に置き換えた診断画像を作って目視確認する（キャラクター内部にマゼンタが出ていないか＝穴が開いていないかのチェック）
- 立ち絵（`t01`）は複雑な描き込みがあり誤って絵を傷つけるリスクがあるため、現時点では背景透過をしていない（白背景のまま）。必要になれば同様の処理を検討する
